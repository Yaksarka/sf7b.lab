# Промпт для выполнения: REA → исправление и пересборка sf7b.lab

Выполни доработку существующего sf7b.lab по [подробному ТЗ](SPEC.md). Это задание на реализацию и проверку, а не только на план. Обычные технические решения принимай самостоятельно, без повторных разрешений на согласованные действия. Общайся по-русски, кратко и понятно.

## 1. Контекст и границы

- Папка правил и документации: `<repository>`.
- Существующие исходники: `<repository>`. Сначала проверь фактическую структуру; не создавай второй проект и не переноси исходники автоматически.
- Прочитай действующие AGENTS.md, RTK.md, [STATE.md](../../STATE.md) и SPEC.md. Исторические сведения проверяй перед использованием.
- Это явное новое поручение возобновить разработку. Старое указание об остановке не препятствует этому заданию.
- Пользователь прямо разрешил **внутренний анализ оригинальных APK**: классы/методы, ресурсы, JNI/native, шейдеры и наблюдение выполнения через REA. Обязательный режим чистой комнаты отменён для этого задания; старое ограничение `docs/CLEAN_ROOM.md` здесь не применяется. Не называй такое исследование чистой комнатой.
- One Lab 1.5.3 — главный ориентир **функциональности, дизайна и взаимодействий**. Glitch Lab 1.7.4 дополняет каталог эффектов и вариантов. Не заменяй этот запрос произвольным редизайном в стиле Apple.
- Сохрани название и идентичность sf7b.lab, нативный Android, офлайн-работу, редактируемые документы, полное разрешение и прозрачность. Реализация, значки и встроенные материалы sf7b.lab должны быть собственными; изученные оригинальные шейдеры и ресурсы не переноси напрямую в APK.

## 2. Сначала настрой ADB именно для REA

1. Проверь существование и работоспособность `<local-private-path>`. Если путь изменился, проверь текущий Android SDK, без поиска по всему компьютеру.
2. Найди фактическую регистрацию MCP-сервера REA и способ его запуска. Сохрани резервную копию изменяемой конфигурации, не раскрывая секреты и не меняя другие серверы.
3. Пропиши `REA_ADB_PATH` абсолютным путём в окружении запуска **этого сервера**. Для TOML строка с `/` или буквальная строка с `\` должна разбираться корректно. Не ограничивайся `$env:REA_ADB_PATH` в дочернем PowerShell: уже запущенный MCP-сервер такое изменение не наследует. Глобальный PATH менять не требуется.
4. Используй уже подключённые инструменты и реальные схемы сервера. Не переустанавливай REA и не запускай общий setup без наблюдаемой необходимости.
5. Если окружение требует нового процесса REA, переподключи его доступным способом. Если в текущем чате это невозможно, сохрани checkpoint, объясни одно конкретное действие для перезапуска и продолжай независимый аудит исходников. Не объявляй REA исправленным до проверки из нового процесса.
6. Через REA вызови доступный `inspect_adb_client`, затем `list_adb_devices`. Зафиксируй выбранный бинарник, версию, результат и ограничения. Успех обычного `adb version` доказывает только доступность ADB, не настройку REA. Пустой список устройств не равен ошибке пути.

## 3. Материалы и среда исследования

Используй установленный навык `reverse-engineer-anything` и его применимые Android/native/runtime references. Источники:

- One Lab: `<local-private-path>`.
- Glitch Lab: `<local-private-path>`.
- Выданный ранее sf7b.lab: `<repository>\artifacts\sf7b-lab-debug.apk`.
- Новая baseline-сборка из текущих исходников — отдельный артефакт; не подменяй ею старый APK.

Пути первых двух APK найдены при подготовке задания. **Версии содержимого пока не проверены**: установи package name, versionName/versionCode, SHA-256 и ABI. Имя файла не является доказательством версии. Если One Lab отличается от 1.5.3 или Glitch Lab от 1.7.4, зафиксируй расхождение и запроси только нужную версию; чужую версию не выдавай за целевую.

Сначала используй совместимый локальный эмулятор; USB не является условием старта. Проверь ABI, графику и доступную память. Телефон — только если без него нельзя проверить конкретное поведение или получить A51-метрики. Не сбрасывай существующие работы в приложениях; применяй отдельные тестовые документы.

Реальный проблемный входной файл отдельно не идентифицирован. Ищи только явно предоставленные материалы; не выбирай случайную личную фотографию из Downloads. Если нужен точный файл для воспроизведения, задай один адресный вопрос и продолжай другие проверки. Наличие всех нужных наборов/доступов в оригиналах тоже пока не подтверждено.

## 4. Исследуй три приложения и составь проверяемую карту

- Оригинальные APK исследуй через REA адресно: идентификация → реестры эффектов и параметров → фактические связи Java/Kotlin, JNI, native, шейдеров → проверка выполнения на одинаковых тестовых входах.
- Сохраняй факты о формулах, режимах, диапазонах, seed, alpha, краях, цвете и масштабировании; отделяй статические доказательства, наблюдения выполнения, гипотезы и неизвестное. Декомпилированный текст может содержать ошибки и не заменяет тест.
- Для sf7b.lab сначала используй полные исходники и обычные инструменты репозитория; REA применяй к поставленному APK и неизвестному поведению, где это добавляет доказательства. Сравни старый APK, текущий код и новую baseline-сборку.
- Зафиксируй ключевые экраны One Lab: проекты/открытие, редактор, браузер эффектов, параметры, дерево/слои, инструменты, экспорт, темы и клавиатура. Сохрани снимки, состояния и переходы. Дизайн реализуй по этим наблюдениям, включая компоновку и управление, с собственной графикой sf7b.lab.
- Сначала пять эффектов: Patchwork Break, Low Freq Banding, Multi Distort, Random Pixelate, Bloom. Затем весь установленный каталог эффектов и наборов для статических изображений. Не сужай итоговый объём до пяти фильтров.
- Подготовь воспроизводимые фото/сетки/градиенты/прозрачные тесты; сохраняй пары вход–экспорт и настройки. Не требуй, чтобы пользователь вручную исследовал всю библиотеку.
- Держи EFFECT_PARITY.md с отдельными статусами: найдено → механизм исследован → реализовано → проверено → сравнено. Для детерминированных случаев измеряй различия; для случайных учитывай доступность seed. Не объявляй полное совпадение без подтверждения.

## 5. Исправляй существующее приложение и собирай результат

Защити существующие исходники, проекты и подпись. Сначала checkpoint и baseline; затем импорт/цвет, производительность, сохранность проектов, модель документа и инструменты, эффекты, интерфейс и полная проверка по SPEC.md. Исследование оригиналов веди параллельно независимым исправлениям. Не откладывай очевидные дефекты собственной sf7b.lab до окончания всего анализа.

Обязательные результаты: автоматический импорт PNG/JPEG/WebP с корректным цветом; быстрый предпросмотр и полный экспорт из исходников; независимые переносимые проекты; поддержка обычного документа с 15 слоями (фактические пределы определяются памятью), маски, Undo/Redo, редактирование ранних эффектов, текст/TTF и рисование; сохранение seed и ресурсов; RU/EN с английскими именами эффектов; дизайн, максимально близкий по компоновке и работе к One Lab, с оговорёнными в SPEC.md дополнениями sf7b.lab.

Проверяй реальные действия, не наличие кнопок. Производительность измеряй до/после; эмулятор не доказывает скорость на A51. Недоступные режимы/наборы и непроверенные эффекты перечисляй явно. Не выдавай цель за достигнутую метрику, компиляцию за проверку телефона, приблизительный аналог за точное совпадение.

После существенных этапов обновляй канонический STATE.md и связанные отчёты, сохраняя точные команды, доказательства, ошибки и следующий шаг. Сессии REA закрывай по инструкции; повторно используй подходящие сохранённые результаты. При нехватке контекста оставь checkpoint, не начинай исследование заново.

В конце предоставь исходники, новый устанавливаемый APK с путём и SHA-256, проверку подписи/возможности обновления, краткую инструкцию установки и отчёты из SPEC.md. Финал: что исправлено; где APK; что измерено; что подтверждено сравнением; что осталось. Продолжай доступную работу без вопросов «продолжать?».
